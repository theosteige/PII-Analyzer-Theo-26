Abstract

The widespread adoption of Large Language Models (LLMs) has introduced a significant privacy concern: users routinely share Personally Identifiable Information (PII) in their prompts, often without realizing the cumulative risk this poses across a conversation. While individual messages may seem harmless, the combination of details shared over multiple prompts—such as a location, an employer, and an age—can make a user uniquely identifiable. To address this, we built a privacy-aware chat interface that detects PII both within individual prompts and across the full span of a conversation, and presents real-time feedback to the user before their message is sent. The system combines Microsoft Presidio's entity recognition with custom pattern-based recognizers, coreference resolution, and LLM-based cross-message analysis to identify retroactive, combinatorial, and disambiguation-based privacy leaks. An identifiability score provides a running measure of how identifiable the user has become. To evaluate the effectiveness of this interface, we conducted a user study in which participants were randomly assigned to either a standard chat interface or our privacy-aware interface and asked to complete a task with the help of an LLM. The data was analyzed to determine whether the privacy-aware interface reduced the frequency and severity of PII shared during the conversation. Design
System Design

This project is implemented as a Flask (Python) web application, following a client-server architecture where the frontend makes API calls to the backend, which serves as the single source of truth for session state. Each user is assigned a UUID-based session identifier, stored via Flask's session cookie mechanism, and all conversation data—messages, detected PII entities, and cached inferences—is maintained in-memory on the server. This means there is no database and all session information is lost on server restart. This is a deliberate simplicity tradeoff appropriate for a research prototype. The server initializes singleton instances of each core component at startup (PIIAnalyzer, ProfileBuilder, InferenceEngine, ContextAnalyzer, and SessionManager), which are shared across all requests. Notably, the system is designed to degrade gracefully: if no OpenAI API key is configured, chat replies and all inference features disable themselves, while the core PII detection pipeline (Presidio + custom recognizers) continues to function independently.

In terms of the actual detection method, there are multiple layers working together. The first layer handles PII detection within each individual prompt. To do this, we use Microsoft Presidio's AnalyzerEngine, which recognizes standard pieces of private information including SSNs, email addresses, phone numbers, credit cards, and approximately 40 other entity types (including international government IDs like UK NINOs, Indian Aadhaar numbers, etc.). On top of Presidio's built-in recognizers, we register five custom regex-based PatternRecognizers that target PII categories more specific to conversational contexts: education (e.g., "college student", "degree in"), occupation (e.g., "engineer", "work at"), relationship (e.g., "my sister", "married"), age (e.g., "I'm 25 years old", "in my thirties"), and health (e.g., "diagnosed with diabetes", "my therapist"). Each recognizer pattern has a tuned confidence score reflecting how reliably that pattern indicates true PII—for example, an explicit age statement like "I am 25 years old" receives a confidence of 0.85, while a vaguer work context pattern like "my job" receives 0.5. We set a global confidence threshold of 0.4, meaning any detection below that threshold is silently discarded. Above that threshold, the confidence score informs the urgency of the feedback shown to the user: lower confidence detections produce more cautious messaging, while high-confidence detections trigger stronger warnings. It is important to note, however, that confidence scores do not directly factor into the identifiability score calculation—once an entity passes the 0.4 threshold, it contributes to the identifiability score based only on its category and uniqueness, not its confidence level.

The next layer of this system addresses the core focus of this research: PII recognition across the span of multiple prompts. In this layer, we employ two complementary techniques to identify PII that only becomes apparent when information from different messages is combined. The first technique is coreference resolution, implemented using the fastcoref Python library. Before each prompt is sent, we concatenate it with all prior messages in the conversation (both user messages and assistant replies) and run the fastcoref model over the full text. This resolves pronoun chains—for example, linking "she" in message 4 back to "my sister Sarah" in message 1—by mapping character-level spans back to their originating messages using boundary tracking. We filter the results to only retain coreference chains that span multiple messages or involve the current draft, since single-message chains are already handled by the per-prompt layer. The second technique uses an LLM (GPT-4o-mini in this implementation, though a data-private open-source model would be used in production) to detect three specific types of cross-message connections. The first type is retroactive, which occurs when a later message makes an earlier vague reference identifiable (e.g., prompt 1: "I was talking to my sister about X", prompt 4: "Yeah, my sister Sarah really knows what she's talking about because she's a doctor"). The second is combinatorial, where individually innocuous pieces of information from different messages combine to narrow someone's identity significantly (e.g., prompt 1: "what's the weather in Schenectady", prompt 2: "Go Garnet Chargers!", prompt 3: "help me with my CS homework"—together suggesting the user attends Union College). The third type is disambiguation, where vague references become specific through accumulated context (e.g., prompt 2: "my doctor said I should rest", prompt 5: "I have an appointment at Albany Med"—the vague "my doctor" is now tied to a specific institution). The LLM is prompted to return structured JSON findings with confidence scores, and results below 0.5 confidence are filtered out. Both coreference and LLM findings are merged, deduplicated (by the set of involved messages and warning type), and sorted by severity (HIGH > MEDIUM > LOW) then confidence.

The final relevant component of the detection system is the identifiability score, which serves as a privacy budget visible to the user. This score ranges from 0 to 100 and represents how identifiable the user has become based on the cumulative PII shared across the conversation. The score is calculated by categorizing all detected PII entities into twelve categories, each with a different weight reflecting its identifying power (e.g., government_id: 30, identity: 25, contact: 20, location: 15, employment: 10, education: 10, and so on down to temporal: 2 and vehicle: 2). To prevent inflated scores from repeated information, diminishing returns are applied: the formula `weight × min(count, 3) / 3` means that the first unique value in a category contributes the most, the second and third add progressively less, and any beyond the third add nothing. Additionally, combination bonuses reward detection of especially identifying pairings: sharing both a name and location adds +15, while location paired with either education or employment each adds +10. The total is capped at 100.

Now that we have established the three main layers of detection that inform the interface, we can describe how data flows through the system in practice. The critical design constraint is that all feedback—identifiability score changes, detected PII highlights, and cross-message warnings—must be presented to the user *before* the prompt is sent, since detection after the fact cannot influence behavior. To achieve this, the frontend calls the `/analyze-preview` endpoint on a debounced 500ms interval as the user types. This endpoint runs the full Presidio analysis on the draft text (without storing it), then calculates the identifiability score delta by building two temporary profiles: one with only the existing session entities, and one with the existing entities plus the preview entities. The difference between these two scores is the projected impact of sending the current draft. Separately and in parallel, the context analyzer runs both coreference resolution and LLM-based cross-message analysis on the draft against the full conversation history. The endpoint returns the detected entities, the current and projected scores, the score delta, any new entity types not previously seen in the conversation, and any cross-message context warnings. The frontend then uses all of this information to update the interface in real time—highlighting PII in the text area, displaying the projected score change, and surfacing warnings—ideally preventing the user from sending the prompt if it contains sensitive information.

Interface Design

The central design principle of this interface, informed by our research question, is that all privacy feedback must reach the user while they are still composing their message—not after it has already been sent. To achieve this, the interface uses a two-panel layout: a chat panel on the left where the user converses with the LLM, and a persistent PII profile sidebar on the right that remains visible at all times. The sidebar displays four sections: (1) the identifiability score, rendered as a color-coded progress bar that transitions from green (low, under 25) to yellow (moderate, 25–49) to orange (high, 50–74) to red (critical, 75+), accompanied by a plain-language description of the user's current risk level; (2) an AI-generated quick inference that summarizes, in 2–3 sentences, what can be deduced about the user from the information they have shared so far; (3) a category breakdown showing each type of detected PII (identity, contact, location, etc.) with a colored border, icon, count badge, and individual value tags listing exactly what has been identified; and (4) a summary section aggregating all known information. By keeping this profile persistently visible alongside the conversation, the user is constantly reminded of the cumulative privacy cost of their messages, rather than only being alerted at the moment of a specific detection.

Within the chat panel itself, the most critical interface element is the real-time preview system that operates directly in the text input area. As the user types, detected PII is highlighted in-line using a transparent overlay positioned behind the textarea—each entity type is assigned a distinct color (19 unique colors across categories), so a user can visually distinguish between, for example, a location (yellow) and a health condition (pink) at a glance. When PII is detected in the draft, a "PII Impact Preview" panel slides down between the chat history and the input area. This panel shows the projected identifiability score change (e.g., "32 → 47 (+15)"), lists any new PII categories that would be introduced by sending the message, and displays the total count of PII items detected. If cross-message connections are found, they appear in this same panel as severity-graded warning cards—each with a type-specific icon (a link icon for coreference, a puzzle piece for combinatorial, a history icon for retroactive, a map pin for disambiguation), a colored left border indicating severity (red for high, yellow for medium, blue for low), the relevant source quotes from prior messages, and a confidence percentage. Once a message is actually sent, the PII remains highlighted within the chat history with tooltips showing the entity type and confidence score on hover, and a count badge below the message indicates how many PII items were detected. The user can also trigger an on-demand detailed analysis via a modal that presents a comprehensive, LLM-generated privacy report explaining how all shared information combines to make them identifiable. The cumulative effect of these design choices is an interface where every visual signal—color, position, motion, and language—is oriented toward making the user aware of privacy risks at the earliest possible moment, before the information leaves their control.
