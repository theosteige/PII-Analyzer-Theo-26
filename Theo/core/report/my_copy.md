Abstract 

Large Language Models (LLMs) have quickly taken over the minds of knowledge workers across the world. The lack of awareness around what is done with data sent to LLM Chatbots can, however, encourage users to input Personally Identifiable Information (PII) into their prompts, raising concerns for users’ security. To raise user awareness in terms of information that should not be given to LLM chatbots, I am building a PII analyzer to examine user inputs across the span of a conversation, in order to find any potential PII issues for the user so that they are aware of the risks associated with sharing PII. To assess the design and efficacy of the tool, I conducted a user study In this study, I asked users to complete an arbitrary task, with the help of an LLM. Users were also arbitrarily assigned to you a default chat interface, or, the chat interface that I built to prevent PII being shared with the model. Introduction and background

It has become clear in the last 4 years the LLMs are being included in the daily workflow of billions of people across the world. Of course, this adoption of new technology provides a number of benefits for its users, however, on the flip side of things, there are also a handful of drawbacks that need to be addressed. Specifically, we focus on the sharing of personally identifiable information. The sharing of such information poses a significant privacy risk to users for a handful of reasons. Firstly, allowing LLM providers access to PII is encouraged by the use cases of such models. In other words, the reasons that people use LLMs often involve dealing with sensitive data. In a study conducted by Deloitte, it was found that the top capabilities organizations are currently investing in for generative AI are content creation, coding, customer service and summarization. In all of these cases, especially for enterprise customers, the models are required to deal with sensitive information like API keys, login credentials, person specific information and more. Along with this, it is a huge security risk to share these sensitive pieces of information, because as the models grow smarter and smarter, your data lives on the servers of your LLM provider, and can potentially be breached or abused to train new models, provide information to people you don’t consent to or more. Finally, LLMs are not designed to handle regulated data like health, financial, etc. in compliance with laws like HIPAA and GDPR, and sharing such data could put you at risk.

Along with these significant risks, we can also use some historical evidence in order to assert the fact that we do not want LLM providers to have our data. For example, one of the premier LLM providers, Meta, experienced a pretty significant breach in data control and consent during the cambridge analytica scandal. During this scandal, users' information was unfairly collected and shared to third parties, in order to influence the 2016 US presidential election. The key issue in this case, is not only that the data was collected unfairly, but mainly, that in fact this sensitive data was shared with a handful of sources, without requesting the users consent. This alone should be enough to persuade users not to share PII with these LLM providers, however, as is the core aspect of my research, users often aren’t even aware of situations where they are sharing this information.

In order to address these issues, I have created an LLM interface that detects PII that the user shares with the LLM, and alerts them of the dangers of sharing this information, before it is too late. Specifically, this research emphasizes the need to detect PII over the course of a conversation rather simply just on a prompt by prompt basis. To do this, I have implemented a complex workflow, that dynamically checks the users prompt for PII risks, using the prompts sent prior in the conversation as necessary context. Design
System Design
This project is implemented as a flask (Python) app, where the frontend (and HTML file), is making API calls to the backend, which manages the state of the session that the user is in. To handle data persistence, users are assigned UUID session identifiers, which are then stored using Flask’s session cookie mechanism, and all relevant data to the user (messages, responses, PII entities, etc.) are stored in memory on the server. This means that we don’t need to have a database, data is not persistent across different sessions, and all data is lost on the webpage refresh.

In terms of the actual detection method, there are multiple layers working together. The first layer handles PII detection within each individual prompt. To do this, we use Microsoft Presidio's AnalyzerEngine, which recognizes standard pieces of private information including SSNs, email addresses, phone numbers, credit cards, and approximately 40 other entity types (including international government IDs like UK NINOs, Indian Aadhaar numbers, etc.). 
On top of Presidio's built-in recognizers, we register five custom regex-based PatternRecognizers that target PII categories more specific to conversational contexts: education (e.g., "college student", "degree in"), occupation (e.g., "engineer", "work at"), relationship (e.g., "my sister", "married"), age (e.g., "I'm 25 years old", "in my thirties"), and health (e.g., "diagnosed with diabetes", "my therapist"). It's important to note here, that for both of the PII identification techniques mentioned above, confidence scores are given whenever certain sections of the users prompt are identified as pieces of PII that shouldn’t be shared with the model. These confidence scores help inform the feedback that the user gets before they send the specific prompt. For example, a lower confidence score will show more relaxed messaging urging the user not to share that information with the LLM, whereas very high confidence scores will lead to more calls to action for the end user. Finally, we set a global confidence threshold of .4, which means that any detected PII below that threshold are not considered important enough to inform the user about. 

The next relevant layer of this system deals with the main focus of this research, which deals with PII recognition across the span of multiple prompts. In this layer, we use a handful of techniques, to help identify PII that is uncovered throughout 2+ prompts. The first recognizer that is used in this layer deals with coreferencing, and helps us understand which portions of which prompts reference the same person. In order to do this, we use a python library called “fastcoref”. In terms of how the library is actually used, before each prompt is sent, we concatenate it with all of the other prompts that the user has sent and using the fastcoref library, can tel which pronouns are referring to which person. This becomes useful in later steps to determine how we are actually connecting pieces of information from throughout the user's conversation. The next method that is employed in this layer may at first seem counterintuitive, but with a few correct choices, becomes much more useful for the end user. This method uses an LLM (4o in this project, but would be open source data private LLM in production) in order to identify three types of connections that can be made throughout a conversation. The first type of connect is retroactive, which happens when a later message makes an earlier vague reference much more identifiable (e.g. prompt 1: I was talking to my sister about X, prompt 4: Yeah, my sister sarah really knows what she is talking about because she is a doctor). The next connection type is a combinatorial connection, where multiple little pieces of information are combined in order to form a much more detailed piece of information (e.g.prompt 1: whats the weather in schenectady, prompt 2: Go Garnet chargers, prompt 3: Help me with my CS homework). Finally we have the third type of connection that can be identified by an LLM, which is disambiguation. This happens when vague references are made more specific through the accumulation of context throughout the conversation. (e.g. TODO).

Our final relevant aspect of the PII detection in this project is the Identifiability score, otherwise known as the privacy budget. This can be seen in the top right of the chat interface, where the user is given a score 1-100 corresponding to how well the LLM can identify them, based on the conversation that they have had. This score is calculated using each of the pieces of PII that are identified. Specifically, different categories of PII have different weights (e.g., government_id: 30, identity: 25, contact: 20, location: 15). From there we employ a few simple calculation methods in order to get more accurate identifiability scores. For example, sharing an email 3 times will not result in a 3x higher identifiability score, but rather, the weight of each piece of PII shared diminishes depending on how many times the same type of PII has been identified. Along with this, scores go up a fixed amount when certain pieces of information are both shared with the model (e.g. name + location = +15). Scores are all capped at 100.

Now that we know the 3 main layers of detection, that help inform our decisions of how the interface is shown to the user, we can talk a bit about the way that data flows in this project. The key finding here is that all information given to the user (identifiability score, PII detected, etc.) need to be given to them before the prompt is sent, otherwise, our detection methods had no effect on the users actual behavior. To do this, we use call an API endpoint every 500ms in order to update the interface as the user is typing in their prompt. Specifically, we post the prompt that the user is writing to the analyze-preview endpoint, then the presidio analysis is done to look for PII to be detected, and then we look at the change in identifiability score, show that to the user, after which we analyze the entire conversation to get the full picture of how much information is being shared with the model by sending that specific prompt. To do this, as mentioned before, we use the fastcoref library to check for coreferencing, and we feed in necessary context to our LLM that is then used to generate any new entities detected, the change in identifiability score, and any warnings we may want to show the user. From there the users interface is updated with the relevant information, and in the perfect world, that interface prevents them from sending the prompt, if it contained PII.

Interface Design
The cmain design principle that we took into consideration when designing the interface, is that all privacy feedback must reach the user while they are still composing their message. In order to do this, the interface makes use of a two panel layout, where the right side is the chat interface that the user sends messages to the LLM using, and the right side is a persistent PII profile that is always visible to the user. The sidebar shows four different sections, each informing the user about what they should and shouldn’t share with the LLM and how much they have already shared. Firstly the identifiability score shows a progress bar which changes color depending on what the users score is at the time. Higher score will turn the bar red, and lower score will turn the bar green. As the users identifiability score increases, the bar fills out. Next, there is an AI generated summary, that breaks down what the model can identify about the user taking into account that messages that they have already sent to the LLM. The third section shows a breakdown of the types of PII that have been detected in the users chat with the LLM. This breakdown includes identity, contact info, location, etc. Finally there is a summary section that puts together all of the PII recognized in the users conversation. These pieces play a key role in informing the user at all times about how much the model knows about them. 

Looking into the chat panel itself, this is where arguably the most important interface elements live.  As the user types, detected PII is highlighted in line, using a transparent overlay whose color is determined by the type of PII that is being highlighted. When PII is detected in the draft (before the user has sent the message) a PII impact preview panel is revealed between the chat itself and the users input. This panel showns the projected identifiability score change, and lists any and all new PII categories that would be revealed by sending the message. It also gives a brief overview of the total number of PII items detected. If connections are found using the cross message logic, they appear in this same panel, with severity graded warnings and icons corresponding to the way they were identified (coreference, combinatorial, etc.). Once a message is actually sent, the PII remains highlighted within the chat history with entity type and confidence scores available to the user if they hover over the highlighted section. In the end, these design choices aim to make the interface visually digestible, easy to understand, and effective at preventing users from sharing these sensitive pieces of information. Along with this, we emphasize that the interface updates before messages are sent to support our original research goal of spreading awareness of the risks associated with sharing PII with these LLMs.
